# How to manage the backup library, retention and drills

Three things that answer one question: are the backups you have any good, and
are you keeping the right ones?

## The library

```bash
dbsync library                  # the app's backup folder
dbsync library --dir /backups   # somewhere else
dbsync library --json           # for monitoring
```

It reads each artifact's manifest and reports sizes, growth over time, and any
backup that came out **dramatically smaller than the one before it**.

**It exits non-zero on a shrink warning**, which makes it usable as a cron check
on its own. That is the failure nothing else notices: the artifact is valid, its
checksum matches, and it restores — it is only wrong relative to yesterday.
Usually a table stopped being selected or a `WHERE` filter changed.

The app's **Library** page shows the same, with the size history per database and
per-artifact actions: check, delete, push off-site.

## Retention

Two independent policies. Neither is on unless you set it.

**Local**, on the schedule:

- keep the last N artifacts
- delete anything older than D days

**Off-site**, on the destination:

```bash
dbsync destination retention off-site --keep-last 30 --max-age-days 90
```

Nothing is deleted that a policy does not name.

## Drills

A drill restores the newest artifact in a directory into a scratch database,
checks it against its manifest, and drops it.

```bash
dbsync drill staging                     # newest in the default directory
dbsync drill staging --dir /backups
dbsync drill staging --deep              # read every row, not just count
dbsync drill staging --keep-on-failure   # leave the wreckage for the morning
```

It exits non-zero if the restore or the check failed, so cron and CI report a
backup that has quietly stopped being restorable.

**A drill cannot touch an existing database.** The scratch name is generated by
the engine and nothing else is droppable. A drill that passes always cleans up,
whatever `--keep-on-failure` says.

### On a timer

```bash
dbsync schedule add-drill nightly-drill staging "0 5 * * *" --deep
```

Run it an hour after the backup it is meant to prove.

### What a drill actually compares

| The backup recorded | The drill can say |
|---|---|
| Row counts (`--count-rows`) | Exact numbers matched, per table |
| No row counts | Each table arrived; a table that restored empty is reported as **not compared**, not as passing |

A manifest without row counts cannot tell an empty restore from a table that was
empty at the source, so it says so rather than guessing. If you want exact
comparison, back up with `--count-rows` and accept the scan.

`--deep` reads every row rather than counting, which catches content corruption
that a count cannot.

## A monitoring setup that works

```bash
dbsync drill staging   || alert "backups are not restorable"
dbsync library         || alert "a backup shrank"
```

Two commands, two distinct failures, both actionable.

## Troubleshooting

| Symptom | Cause |
|---|---|
| Drill fails immediately on checksum | The artifact is truncated or altered |
| Drill reports "not compared" everywhere | The backup did not record row counts |
| `library` exits non-zero and nothing looks wrong | A shrink warning. Compare the table list against the previous run. |
| Scratch database left behind | The drill failed with `--keep-on-failure` set. Drop it when done. |
| Retention deleted nothing | No policy set, or nothing is old enough / over count |
